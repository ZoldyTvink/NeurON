# Чат: быстрые ответы и данные пациента

Веб-чат использует ту же модель `meditron-gigachat` в Ollama. Переобучение и
облачный API не нужны. Настройки URL, имени модели, провайдера и keep-alive
сохраняются. Старый `MEDITRON_CHAT_MODE=router` можно оставить в `.env`: шаблонный
маршрутизатор больше не подключается к веб-чату. `/api/config` сообщает `mode=hybrid`.

## Три пути обработки

Чистые разговорные реплики («ясно, спасибо», приветствие, прощание) передаются
сразу в генерацию GigaChat с историей, без планировщика чтения данных. Готового
текста ответа для них нет. Для остальных формулировок планировщик получает правило
и пример завершения беседы: благодарность сама по себе не требует медицинской
сводки. Благодарность с новым вопросом сохраняет обычный путь обработки запроса;
короткие «да»/«нет» интерпретируются моделью по истории.

1. Узкий набор команд, например «Открой календарь» и «Хочу записаться к врачу»,
   распознаётся точным совпадением нормализованной фразы без вызова модели.
   Отрицания, несколько целей, дополнительные условия и неоднозначные фразы
   не попадают в этот быстрый путь. Числовой «100% уверенности» нет.
2. Однозначные вопросы о данных («Какие препараты мне сегодня принимать?»,
   «Сколько препаратов мне нужно принять сегодня?», «Что осталось принять
   сегодня?», «Какие у меня документы?») обслуживаются запросом к БД. Ответ
   содержит сами данные, а кнопка только дополняет его. Эти пути работают даже
   при недоступной Ollama.
3. Остальные сообщения получает выбранная GigaChat вместе с историей и временем
   пациента. Отдельный короткий шаг распознавания возвращает до четырёх разделов в
   `queries` и вид ответа: `list` (перечень/количество) или `explain` (объяснение). Сервер читает только данные авторизованного пациента.
   И для `list`, и для `explain` модель получает результаты и
   формулирует ответ на последнее сообщение. Ошибочный план чтения данных сам по
   себе больше не превращает благодарность в серверный список. Поэтому возможны
   два вызова модели. Промежуточная фраза не показывается
   и не сохраняется в истории. Повторного цикла инструментов нет: при нехватке
   данных требуется уточнение.

   Если разговорная модель также выбирает экран запрошенных данных для `list`,
   сервер сохраняет полный точный список вместо сокращённого пересказа. Ответ
   с `action=none` имеет приоритет над списком и возвращается как написан моделью.

## Доступные данные

- `medications`, `medications_taken`, `medications_remaining`, `medications_skipped`
  и `calendar` преобразуются сервером в чтение `schedule`: полный календарь указанного периода, время в часовом поясе пациента,
  сохранённая дозировка, заметки, источник и отметки. По умолчанию сегодня.
  Внутренний фильтр `scope=medications` включает препараты и витамины, исключает еду и привычки. Модель выбирает отдельный код medications, а не сочетание независимых флагов.
  `status=remaining` означает pending/snoozed, а не рекомендацию принять пропущенное.
- `plans`: назначения внешнего врача, схема, статус добавления в календарь.
- `courses`: назначенные и личные курсы с прогрессом.
- `appointments`: сохранённые записи, включая отменённые с явным статусом.
- `documents`: только анализы и справки, их содержание и сроки действия.
- `observations`: сохранённые наблюдения.

Для периода разрешено до 63 дней в пределах года от текущей локальной даты.
У назначений период относится к дате публикации, у документов — к дате выдачи,
у курсов — к пересечению периода курса. Отсутствие записей не означает отсутствие
лечения вне сервиса. Неполные результаты явно помечаются.

В модель отправляются последние 24 сообщения в пределах 8000 символов вместе
с текущим вопросом. Для объяснения результаты чтения ограничены общим бюджетом 14000 символов
(поровну между запрошенными разделами); `truncated=true` запрещает выдавать их
за полный список. Если одна запись не помещается, она не отправляется, результат
помечается неполным. Прямой ответ по БД использует полную выборку, но при превышении
размера сообщения честно сообщает, что показана часть списка. В Ollama задан
`num_ctx=16384`, максимальный ответ — 1200 токенов. Полная история БД не вставляется
в каждый промпт. Для одного периода календаря сохраняется первая (основная)
выборка планировщика: повторные более широкие выборки не подмешиваются к ответу
о только принятых препаратах.

Инструменты не меняют дозировку, отметки, покупки или записи. Создание недостающих
экземпляров расписания — идемпотентная техническая операция календаря. Она
фиксируется до повторного вызова модели, чтобы не держать блокировку SQLite.

## Проверка

На текущие жалобы модель уточняет симптомы, предлагает запись и напоминает:
если сейчас очень плохо или состояние резко ухудшается — звонить 112 или 103,
не ждать записи. При явно опасных симптомах немедленный вызов имеет приоритет.
Собственные советы по лечению, препаратам, дозировкам и домашним средствам
запрещены; сохранённые назначения можно только пересказать по запросу с указанием
источника. `tests/live_wellbeing_smoke.py` проверяет эти ответы на локальной модели
на вымышленных репликах без доступа к данным пациента.

`tests/live_assistant_data.py` — отдельная явная проверка через настоящую локальную
Ollama на вымышленном пациенте во временной БД. Не использует рабочую базу.

`tests/test_assistant.py` проверяет неоднозначность, отрицания, полный день с более
чем 24 событиями, часовые пояса, отмены и отметки, изоляцию пациентов, получение
данных моделью, историю, ограничения и работу без модели. Остальные API/транспортные
тесты проверяют JSON, ошибки и сохранение переписки. Тесты используют временную БД.

Скорость старого маршрутизатора не описывает новую схему: быстрые пути не вызывают
модель, а сложные вопросы могут потребовать два вызова. Гарантия 3–5 секунд для
всех запросов отсутствует; зависит от оборудования, объёма данных и длины ответа.
`router_nlu.py` и прежние benchmark/eval-скрипты оставлены для сравнения старого
маршрутизатора, но веб-чат его не использует.

Последняя локальная проверка 05.10.2026 на синтетических данных: прямой вопрос
0,16 с; свободная формулировка 3,13 с; уточнение по истории 6,57 с. Это один
прогон с прогретой моделью, не гарантия задержки и не оценка точности на всех
формулировках. При первых прогонах обработка свободного запроса занимала 10–15 с.
