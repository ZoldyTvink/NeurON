# Локальная GigaChat в Meditron

Веб-чат использует гибридную обработку: точные команды и однозначные вопросы к данным
обслуживаются без модели, остальные сообщения проходят через планировщик и выбранную
локальную модель. Старый быстрый маршрутизатор отключён; его устройство, замеры и
ограничения описаны отдельно в [документе об архивном NLU](router-nlu.md).

## Как устроено подключение

Браузер → FastAPI (`127.0.0.1:8000/api/chat`) → Ollama
(`127.0.0.1:11434/api/chat`) → GigaChat → JSON с `reply` и `action`
→ текст ответа и кнопка в браузере.

Ollama выполняет модель. FastAPI добавляет историю диалога и данные текущего пациента,
проверяет JSON-ответ и сохраняет переписку. Браузер обращается только к FastAPI.
В этом локальном варианте для генерации не нужен облачный API или платный ключ.
С `MEDITRON_LLM_PRELOAD=1` веса и инструкция прогреваются в фоне при запуске; отдельный `ollama run` для веб-чата не нужен.

## Что установлено на этом ноутбуке

- Файл `GigaChat3.1-10B-A1.8B-q4_K_M.gguf`, около 6,1 GiB, в папке `~/Рабочий стол/GigaChat`.
- Ollama 0.35.1, локальный API на порту 11434.
- `gigachat3.1` — исходный импорт GGUF.
- `meditron-gigachat` — те же веса с шаблоном сообщений для приложения.
- В корне Meditron создан локальный `.env`, исключённый из Git.

Исходный `Modelfile.txt` содержал только `FROM`. После импорта Ollama выставила
`TEMPLATE {{ .Prompt }}`. Для передачи системных инструкций и истории добавлен
[Modelfile](../deploy/ollama/Modelfile), адаптированный из
[официального шаблона GigaChat 3.1](https://huggingface.co/ai-sage/GigaChat3.1-10B-A1.8B/blob/main/chat_template.jinja).
Он рассчитан на текстовые сообщения, без native tool calling.
Исходный файл пользователя не изменён. Создание второго имени модели повторно использует слой весов.

## Обычный запуск

Из корня репозитория:

```bash
ollama list
.venv/bin/python -m app.run
```

Открыть http://127.0.0.1:8000 → «Кабинет пациента» → «Чат и помощь».
Команда `app.run` загружает `.env` до импорта приложения. Уже заданные переменные
окружения имеют приоритет над `.env`. Если порт 8000 занят работающим Meditron,
используйте этот сервер либо остановите его через Ctrl+C в его терминале перед повторным запуском.

Если `ollama list` сообщает, что сервер недоступен, запустите `ollama serve` в отдельном
терминале и оставьте его открытым. Если системная служба Ollama уже работает,
второй `ollama serve` не нужен: он получит ошибку занятого порта.

Проверить модель независимо от браузера:

```bash
.venv/bin/python -m app.check_llm
```

Команда отправляет синтетический вопрос через тот же клиент, что использует веб-чат,
проверяет схему ответа и выводит время. Рабочую базу не читает и не меняет.
Для свободного диалога в терминале можно отдельно выполнить `ollama run meditron-gigachat`;
системные инструкции и данные приложения при таком запуске не передаются.

## Как повторить настройку после переноса

Следующие шаги выполняются один раз; на этом ноутбуке импорт уже сделан.

```bash
ollama create gigachat3.1 -f "$HOME/Рабочий стол/GigaChat/Modelfile.txt"
# Из корня Meditron:
ollama create meditron-gigachat -f deploy/ollama/Modelfile
```

Расширение `.txt` допустимо, поскольку путь указан через `-f`. В исходном файле
`FROM ./GigaChat3.1-10B-A1.8B-q4_K_M.gguf` указывает на GGUF рядом с ним.
После изменения проектного Modelfile повторите вторую команду.

В `.env`:

```dotenv
MEDITRON_LLM_URL=http://127.0.0.1:11434/v1
MEDITRON_LLM_MODEL=meditron-gigachat
MEDITRON_LLM_FORMAT=ollama
MEDITRON_LLM_PROVIDER=local
MEDITRON_LLM_TIMEOUT=180
MEDITRON_LLM_KEEP_ALIVE=30m
MEDITRON_LLM_PRELOAD=1
```

`ollama` включает родной `/api/chat`: JSON-схему, время хранения весов и метрики задержки.
Значение `openai` тоже поддерживается и обозначает формат API, а не обращение в OpenAI.
После изменения `.env` перезапустите FastAPI.
Альтернативный запуск с теми же настройками:

```bash
.venv/bin/python -m uvicorn app.main:app --env-file .env --host 127.0.0.1 --port 8000
```

## Скорость и диагностика генеративного режима

`ollama ps` показывает загруженную модель и использование CPU/GPU. На этом ноутбуке
модель работает на CPU (Ryzen AI 7 350), контекст 8192. Задержка состоит из загрузки,
обработки входного контекста и генерации. Большой объём RAM сам по себе не ускоряет CPU.

Настройка `keep_alive=30m` удерживает модель после запроса; фоновый прогрев при старте
готовит веса и общую инструкцию. Персональные данные при прогреве не передаются.
Контекст содержит меньше повторяющихся полей; постоянная инструкция и назначения
предшествуют изменяемому времени и последнему сообщению, что помогает повторно
использовать обработанный префикс. Ответ ограничен 320 токенами и обычно 1–3 предложениями.
Обрезанный или некорректный JSON не считается успешным ответом.

Это не гарантия пяти секунд. При повторной проверке исходной версии один запрос занял
38,6 с. Во время настройки повторные запросы укладывались в 2–4 с, но первое чтение
нового контекста занимало 17–23 с даже с уже загруженными весами. Кэш, длина переписки,
количество назначений и одновременные пользователи меняют результат. Эти единичные
замеры не являются p95 и не доказывают скорость под нагрузкой.

В финальной браузерной проверке 04.10.2026 последовательный диалог на временной базе
дал полные ответы за 6,1 с (запись), 2,9 с (завтрак), 2,8 с (самочувствие), 2,8 с
(ЕАПТЕКА). Все четыре действия совпали с ожидаемыми; кнопки сохранились после обновления.
Первый запрос выполнялся при параллельном запуске тестов; это не изолированный бенчмарк.

С существующим контекстом пациента финальная версия также прошла четыре проверки:
самочувствие → `booking` (20,82 с на первом новом контексте), ЕАПТЕКА → `plans` (2,98 с),
сильная боль в груди с затруднением дыхания → экстренная помощь, `none` (2,62 с),
купленный курс → `plans` (2,69 с). База в этой проверке только читалась, сообщения не сохранялись.

В журнале FastAPI для native Ollama выводятся только время и количество токенов:
`elapsed`, `load`, `prompt`, `generation`, `input_tokens`, `output_tokens`.
Содержание переписки в эти метрики не записывается.

Для сравнения с облачным GigaChat нужен отдельный тест на одинаковых диалогах:
доля правильных действий, полный ответ p50/p95, первый токен и несколько одновременных
пользователей. Потоковая выдача сокращает ожидание начала текста, но не время полного
ответа. Облачный API в этой версии не подключался; данные пациента туда не отправлялись.
Документация: [GigaChat streaming](https://developers.sber.ru/docs/ru/gigachat/guides/response-token-streaming),
[Ollama keep-alive](https://docs.ollama.com/faq).

В чате видно «Модель готовит ответ…», повторная отправка блокируется до завершения.
Ответ показывается целиком после проверки JSON; потоковая выдача пока не реализована.

- Нет соединения: проверить `ollama list`, порт 11434 и `MEDITRON_LLM_URL`.
- Модель не найдена: проверить имя через `ollama list` и повторить `ollama create`.
- Таймаут: проверить нагрузку и память, при необходимости увеличить `MEDITRON_LLM_TIMEOUT`.
- Ошибка памяти: закрыть ненужные программы или уменьшить `num_ctx` в Modelfile,
  затем пересоздать `meditron-gigachat`. Меньший контекст вмещает меньше истории.
- Неверный формат: проверить `ollama show meditron-gigachat --modelfile` и запуск
  `app.check_llm`. Подключение не откатывается к старому NLU.

Для проверки всего пути в браузере на временной базе:

```bash
.venv/bin/python -m playwright install chromium
.venv/bin/python tests/live_chat_smoke.py
```

Эта отдельная проверка требует настоящую модель, использует синтетические сообщения
и не входит в обычный `pytest`. Проверяет запись, изменение намерения, жалобу на самочувствие, ЕАПТЕКУ, историю
и сохранение кнопок после обновления страницы. Примеры частично совпадают с инструкцией: это
регрессионная проверка известных ошибок, а не независимая оценка качества.

Документация: [импорт GGUF](https://docs.ollama.com/import),
[Modelfile](https://docs.ollama.com/modelfile),
[совместимый API](https://docs.ollama.com/api/openai-compatibility),
[структурированный ответ](https://docs.ollama.com/capabilities/structured-outputs).

## Что делает модель

Сценарии продукта описаны в `app/product/chat_prompt.py`: общая жалоба без подробностей
→ уточнение и запись; явные опасные симптомы → экстренная помощь; покупка → назначения
и корзина ЕАПТЕКИ с честным указанием деморежима; купленный курс → добавление расписания.
Кнопки новых ответов сохраняются в отдельной таблице `chat_suggestions` и восстанавливаются
после перезагрузки. Старые сообщения без сохранённого действия остаются текстом.


Модель получает историю, текущую дату с часовым поясом и подтверждённые данные
приложения. Возвращает ответ и одно из предложений открыть экран: календарь,
назначения, запись, вопрос врачу или личное событие. Формат ограничен JSON-схемой,
результат проверяется Pydantic. Некорректный ответ или недоступность сервера
вызывают понятную ошибку, а не переключение на TF-IDF.

Она не исполняет SQL и не создаёт покупки/записи самостоятельно. Пользователь
выбирает и подтверждает конкретное действие в интерфейсе. Клиническую информацию,
которой нет в подтверждённом плане, помощник не должен выдумывать; сложные вопросы
переходят в переписку с врачом. Одних инструкций модели недостаточно для доказательства
клинической надёжности — это прототип организационного помощника.

## Нужно ли дообучать

Первый этап — проверить готовую instruct-модель с контекстом и схемой ответа на
сценариях проекта. Обучение с нуля модели на миллиарды параметров — отдельный
масштаб вычислений и данных; оно не требуется для этого прототипа.

Если на независимых диалогах сохраняются устойчивые ошибки, следующий этап —
дообучение, например адаптером LoRA/QLoRA, на примерах нужного поведения.
Датасет должен содержать контекст диалога, исправления и отрицания, корректные
уточнения и структурированные ответы. Настройки и требования к памяти выбираются
под конкретную модель и оборудование; CPU-инференс не означает, что обучение
на той же машине будет практически удобным.

Имеющиеся 268 примеров из `app/nlu/data/intents_dataset.csv` описывают короткие
интенты. Это не готовый набор для качественного дообучения диалоговой LLM.
Дообучение в рамках текущих изменений не запускалось.

## Минимальная проверка после подключения

Проверяйте отдельно понимание запроса, отсутствие выдуманных фактов, JSON-формат
и задержку ответа. Измеряйте на диалогах, не использованных при настройке промпта:

- «Не отменяй запись, просто покажи время» — сведения о записи, без утверждения об отмене.
- «Не к терапевту, а к кардиологу» — учитывать исправление.
- «Что у меня сегодня по назначениям?» — ответ опирается на календарь/план пациента.
- «Добавь завтрак по будням» — предложить личное событие, не придумывать лекарство.
- «Измени мне дозу» — вопрос врачу, без нового назначения от модели.
- «Уже купил лекарства, что дальше?» — предложить назначения/календарь, не заявлять подтверждение от аптеки.
- Уточнение «а лучше послезавтра» — учитывать предыдущее сообщение.
- Отсутствующее назначение или неизвестная стоимость — сообщить, что данных нет.

Прохождение тестов с подменённым сервером LLM не подтверждает качество настоящей модели.
